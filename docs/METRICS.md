# 지표 정의와 선정 근거

이 문서는 대시보드에 노출하는 지표를 **왜 골랐는지**, **무엇을 어떻게 계산하는지**,
**어떻게 읽어야 하는지**를 설명한다. 지표는 두 축으로 나뉜다.

- **시장 지표** — "지금 시장이 어떤 상태인가"를 보여준다. 가격·평균 체결 단가·변동성·수급·활동량.
- **운영 지표** — "그 시장 지표를 믿어도 되는가"를 보여준다. 수집 지연·데이터 커버리지·복구 이력·연결 상태.

데이터 파이프라인 과제에서 이 두 축은 동급이다. 모든 시장 지표는 우리가 수집한 1분봉과
체결 원본 위에서 계산되므로, **원본에 결손·지연이 있으면 시장 지표가 그대로 왜곡된다.**
"값이 얼마인가"와 "그 값이 온전한 데이터에서 나왔는가"를 함께 보여주는 것이 이 대시보드의 설계 의도다.

---

## 0. 수치 정확도 원칙 (모든 지표 공통)

1. **집계는 전부 PostgreSQL numeric 연산으로 수행한다.** 가격·수량은 `numeric(24,8)`/`numeric(32,8)`로
   저장되고, 합계·비율·표준편차·로그까지 SQL 안에서 numeric 으로 끝낸다.
   JS 부동소수(double)로 원시 데이터를 누적하면 오차가 쌓이므로 금지한다 (CONTRACT 6절).
2. **API 경계에서만 `Number()` 변환한다.** 최종 스칼라 하나를 표시 목적으로 변환하는 것은
   유효숫자 15자리 이내에서 안전하다 (BTC 가격 + 소수 8자리 ≈ 13자리).
3. **`NaN`/`Infinity` 는 프론트로 절대 내보내지 않는다.** 변환 경계(`toFiniteNumber`)에서 차단한다.
4. **계산 불가는 숨기지 않고 명시적으로 처리한다.** 분모 0, `ln(0)`, 표본 부족은 SQL `CASE` 로
   먼저 걸러 `NULL` 로 표기한다. 스냅샷(overview)은 타입 계약상 number 이므로 0 으로 치환하되
   그 의미를 4절 표에 고정했고, 시계열(series)은 해당 포인트를 **아예 제외**해 0 으로 위장하지 않는다.

## 1. 시장 지표

### 1.1 lastPrice — 최신 체결가

- **정의·계산식**: `trades` 에서 `trade_time DESC, trade_id DESC` 정렬 후 첫 행의 `price`.
  체결이 아직 없으면 마지막 1분봉 `close` 로 대체.
- **선정 이유**: 모든 파생 지표(변화율·이격도)의 기준값이다. 봉 단위가 아닌 체결 단위에서 읽어
  대시보드가 초 단위로 살아 움직이게 하고, 동시에 "수집이 실제로 돌고 있다"는 가장 직관적인 증거가 된다.
- **읽는 법**: 값 자체보다 **갱신되고 있는지**가 중요하다. 가격이 멈춰 있으면 시장이 멈춘 것이 아니라
  수집이 멈췄을 가능성이 훨씬 크다 — 이때 운영 지표(lag)를 함께 봐야 한다.

### 1.2 priceChangePct24h — 24시간 변화율 (%)

- **정의·계산식**: `(lastPrice / close_24h − 1) × 100`.
  `close_24h` 는 `open_time <= now() − 24h` 인 가장 최근 1분봉의 종가 (SQL `ORDER BY … DESC LIMIT 1`).
- **선정 이유**: 거래소·뉴스·트래커가 공통으로 쓰는 가장 보편적인 모멘텀 지표라
  사용자가 별도 학습 없이 바로 읽을 수 있다. "지금 시장 분위기"의 한 줄 요약.
- **읽는 법**: ±1~2% 는 암호화폐에서 평온한 수준. BTC 기준 ±5% 이상이면 뚜렷한 방향성 이벤트.
  **주의**: 24시간 "롤링" 기준이라 기준 시점이 계속 이동한다 — 24시간 전의 급등락이 윈도우에서
  빠져나가는 것만으로 값이 변할 수 있다(기저 효과). 수집 이력이 24시간 미만이면 계산 불가로 0 처리된다.

### 1.3 quoteVolume24h — 24시간 거래대금 (USDT)

- **정의·계산식**: 최근 24시간 1분봉의 `SUM(quote_volume)` (SQL numeric 합계).
- **선정 이유**: 유동성과 시장 참여도의 표준 척도다. base 수량(`volume`)이 아닌 **USDT 거래대금**을
  쓰는 이유는 심볼 간(BTC vs ETH) 비교가 가능하고 가격 수준 변화에 왜곡되지 않기 때문이다.
- **읽는 법**: 절대값보다 평소 대비 추이가 중요하다. 가격 변동이 큰데 거래대금이 늘지 않았다면
  얇은 호가에서 만들어진 움직임이라 되돌림이 쉽다. **주의**: 커버리지(2.2절)가 1 미만이면
  이 값은 과소집계다 — 반드시 커버리지와 함께 읽어야 한다.

### 1.4 vwap — 거래량가중평균가 (최근 N분, 기본 60분)

- **정의·계산식**: `Σ(quote_volume) / Σ(volume)` — 분자·분모 모두 SQL numeric 합계.
  단순 종가 평균이 아니다. 1분봉의 `quote_volume` 이 "그 분의 Σ(가격×수량)"이므로
  분 단위 봉의 합산만으로 전체 구간의 정확한 VWAP 이 나온다.
- **선정 이유**: "이 구간에서 시장 참여자들이 실제로 지불한 평균 단가"다. 기관 트레이딩에서
  주문 집행 품질의 벤치마크로 쓰이는 실무 표준 지표이며, 현재가가 정당한 수준인지 판단할 기준선이 된다.
- **읽는 법**: 현재가 > VWAP 이면 구간 평균 매수자가 이익 중(강세 심리), 반대면 약세 심리.
  **주의**: 거래량이 극단적으로 쏠린 1분이 있으면 그 시점 가격이 VWAP 을 지배한다 —
  이는 버그가 아니라 정의 그 자체이나, 단순 이동평균처럼 읽으면 오해한다.

### 1.5 vwapDeviationPct — VWAP 이격도 (%)

- **정의·계산식**: `(lastPrice − vwap) / vwap × 100`. SQL 에서는 중첩 나눗셈을 피해
  동치식 `(lastPrice × Σvolume / ΣquoteVolume − 1) × 100` 으로 계산한다.
- **선정 이유**: VWAP 과 현재가를 따로 보여주면 사용자가 암산해야 한다. 차이를 %로 정규화하면
  심볼·가격대와 무관하게 "얼마나 평균에서 벗어났는가"를 한눈에 읽을 수 있고, 단기 과열/눌림의
  트리거로 바로 쓸 수 있다.
- **읽는 법**: 양수 = 평균 체결가보다 비싸게 거래 중(단기 과열 가능), 음수 = 평균 아래(눌림).
  **주의**: 이격이 크다고 반드시 회귀하는 것은 아니다. 강한 추세장에서는 이격이 유지·확대된
  채로 가격이 계속 간다. 회귀 신호가 아니라 **위치 정보**로 읽어야 한다.

### 1.6 realizedVolatility — 연율화 실현변동성 (%)

- **정의·계산식**: 최근 N분 1분 로그수익률 `r_t = ln(close_t / close_{t−1})` 의
  표본표준편차(`stddev_samp`) × `√525,600` × 100.
  525,600 = 1년의 분 수(365×24×60). 전 과정이 SQL numeric(`ln`, `stddev_samp`, `sqrt`)이다.
- **선정 이유**: 방향(변화율)만으로는 시장의 "거칠기"를 알 수 없다. 변동성은 리스크의 크기 그 자체로,
  포지션 크기 조절·급등락 국면 감지에 직결된다. **로그수익률**을 쓰는 이유는 시간 가법성
  (여러 구간 수익률의 합 = 전체 구간 수익률)이 성립해 √t 연율화가 수학적으로 정당하기 때문이고,
  **연율화**하는 이유는 "연 45%"처럼 자산·기간 간 비교 가능한 단위로 만들기 위해서다.
- **읽는 법**: BTC 는 연 30~60% 가 평시 범주, 100% 이상이면 급등락 국면이다.
  **주의점 세 가지**: (1) 60분 표본의 연율화는 "지금 이 순간의 변동성 체감온도"이지 연간 예측치가
  아니다. (2) 표본이 2개 미만이면 표준편차가 정의되지 않아 계산 불가 처리한다(0 으로 위장하지 않고
  SQL `NULL` → 4절 정책). (3) `close ≤ 0` 봉은 `ln` 정의역 밖이라 SQL 필터로 제외한다.

### 1.7 takerBuyRatio — 체결강도 (0~1)

- **정의·계산식**: 최근 N분 `Σ(taker_buy_quote) / Σ(quote_volume)` — SQL numeric 비율.
  taker buy = 시장가 매수(매도 호가를 걷어간 체결). 분모 0 이면 계산 불가 처리, 결과는 0~1 로 클램프.
- **선정 이유**: 가격·거래량은 "무슨 일이 일어났는가"를 보여주지만, 체결강도는 **누가 공격적이었는가**
  (수급의 방향)를 보여준다. 가격 상승이 공격적 매수 유입 때문인지, 매도 부재 때문인지 구분하게
  해 주는, 체결 데이터가 있어야만 만들 수 있는 지표다 — 이 파이프라인의 데이터가 아니면 못 만드는
  지표를 하나 보여주는 의미도 있다.
- **읽는 법**: 0.5 초과 = 시장가 매수 우위, 미만 = 시장가 매도 우위. 0.55 이상 지속이면 뚜렷한 매수 압력.
  **주의**: 거래가 얇은 구간에서는 소수 체결만으로 극단값(0 또는 1 근처)이 나온다.
  거래대금(1.3)과 함께 읽어야 한다.

### 1.8 tradeCount1m — 최근 1분 체결 건수

- **정의·계산식**: `trades` 에서 `trade_time > now() − 1분` 인 행의 `COUNT(*)`.
- **선정 이유**: 거래대금과 독립적인 **활동량** 지표다. 같은 거래대금이라도 소수 대형 체결과
  다수 소형 체결은 시장 성격이 다르다. 동시에 trade 스트림의 처리량 게이지 역할도 해서
  시장 지표와 운영 지표의 접점에 있다.
- **읽는 법**: 급증하면 이벤트(뉴스·청산) 발생 중. **0 이면 시장이 죽었다기보다 수집 장애일
  가능성이 먼저다** — lag(2.1)와 교차 확인. BTCUSDT 는 평시에도 분당 수백~수천 건이 정상이다.

### 1.9 volumeSurgeRatio — 거래대금 급증 배율

- **정의·계산식**: `최근 N분 Σ(quote_volume) ÷ 직전 N분 Σ(quote_volume)` — 두 구간 모두 SQL 합계.
  직전 구간이 0 이면 비교 기준이 없으므로 계산 불가 처리(분모 0 방어).
- **선정 이유**: 거래대금의 절대값은 심볼·시간대마다 달라 임계값을 정하기 어렵다.
  직전 동일 길이 구간과의 **비율**로 정규화하면 "평소 대비 몇 배"라는 자기 기준 이상 감지가 되어,
  뉴스·대량 청산 같은 이벤트를 심볼 무관하게 잡아낸다.
- **읽는 법**: ≈1 평상시, ≥2 뚜렷한 급증(이벤트 의심), <0.5 급감(관심 이탈 또는 **수집 결손** —
  커버리지 확인). **주의**: 직전 구간 자체가 조용했다면 작은 증가도 큰 배율로 나온다.
  배율과 절대 거래대금(1.3)을 함께 봐야 한다.

## 2. 운영 지표 — 데이터가 온전한가

> 구현은 ops 담당(`/ops/health`)이 맡지만, 선정 근거는 지표 체계의 일부로 여기에 통합해 남긴다.

수집 파이프라인 과제에서 가장 먼저 증명해야 하는 것은 "지표가 그럴듯하다"가 아니라
**"지표의 원료가 온전하다"** 이다. 위 시장 지표는 전부 1분봉·체결 원본의 함수이므로:

- 1분봉이 5% 비면 → quoteVolume24h 는 5% 과소, VWAP 은 빈 구간의 가격대를 반영하지 못하고,
  로그수익률은 갭을 건너뛴 비정상 표본을 만든다.
- 수집이 3분 지연되면 → lastPrice·tradeCount1m 이 "죽은 값"인데 화면은 정상처럼 보인다.

즉 운영 지표는 시장 지표에 대한 **신뢰 구간 표시**다. 아래 네 가지를 고른 이유다.

### 2.1 수집 지연 (lagSeconds)

- **정의**: 스트림별 `now() − 마지막 이벤트 수신 시각`.
- **선정 이유**: 장애의 최전선 신호다. WS 가 "연결됨" 상태여도 이벤트가 흐르지 않는 반쯤 죽은
  연결(half-open)은 lag 로만 잡힌다. 화면의 모든 실시간 값의 신선도를 한 숫자로 보증한다.
- **읽는 법**: trade 스트림은 수 초 이내가 정상. kline 스트림은 갱신 주기 특성상 수십 초까지 정상
  범주다. 스트림별 기대 주기를 넘어 지속 증가하면 재연결·네트워크 문제를 의심한다.

### 2.2 1분봉 커버리지 (coverage)

- **정의**: 최근 24시간 기대 봉 수(1440개) 대비 실제 저장된 봉 수의 비율과 누락 구간 목록.
- **선정 이유**: lag 가 "지금"의 건강도라면 커버리지는 **과거 이력의 무결성**이다. 재시작·순단으로
  생긴 갭이 백필로 실제로 메워졌는지를 정량 증명한다 — "데이터가 온전한가"에 대한 가장 직접적인 답.
- **읽는 법**: 1.0 이 목표. 1 미만이면 누락 구간(missingRanges)을 확인하고, 그 구간이 걸친
  시장 지표(특히 24h 거래대금·변동성)는 보수적으로 읽는다. 최신 1~2분은 봉 확정 전이라
  일시적으로 낮게 보일 수 있다.

### 2.3 백필 작업 성공/실패 (backfill jobs)

- **정의**: `backfill_jobs` 의 실행 중/대기/24시간 내 실패 건수와 마지막 성공 시각.
- **선정 이유**: 갭은 "없어야 한다"가 아니라 "생겨도 스스로 메운다"가 현실적인 목표다.
  백필 이력은 파이프라인의 **자기 치유 능력**이 실제로 작동했다는 증거이고, 실패 누적은
  레이트리밋·API 장애 같은 구조적 문제의 조기 경보다.
- **읽는 법**: failed 가 0 이 아니면 원인(429/네트워크)을 운영 로그에서 확인.
  running/pending 이 계속 쌓이면 weight 예산 대비 갭 발생 속도가 빠르다는 뜻이다.

### 2.4 WS 연결 상태 (stream status)

- **정의**: 스트림별 connected 여부와 연결/끊김/재연결 이벤트 이력.
- **선정 이유**: lag·커버리지 이상이 발견됐을 때 원인을 좁혀 주는 1차 진단 정보다.
  "끊겼는가"(연결 문제)와 "연결됐는데 안 오는가"(스트림/구독 문제)를 구분하게 한다.
- **읽는 법**: 잦은 재연결 반복은 네트워크 품질 또는 서버측 정책(24시간 연결 종료 등) 신호.
  재연결 직후에는 커버리지 갭 발생 → 백필 트리거가 정상 순서다.

## 3. 캔들 파생 집계 규칙 (5m / 15m / 1h)

1분봉만 저장하고 상위 인터벌은 조회 시 순수 PostgreSQL 로 파생한다 (TimescaleDB 미사용).

- **시간 버킷**: `to_timestamp(floor(extract(epoch from open_time) / N) * N)` (N = 버킷 초).
  1분봉 `open_time` 이 분 경계에 정렬돼 있으므로(CONTRACT 7절) 버킷 경계도 정확히 맞는다.
- **open / close 는 시간 순서 기준 첫/마지막이다** — `min`/`max` 가격이 아니다.
  `first_value(open)` / `last_value(close)` 윈도우 함수를 쓰되, **프레임을
  `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` 로 명시**한다.
  기본 프레임은 `... AND CURRENT ROW` 까지라 `last_value` 가 "현재 행의 close"를 돌려주는
  잘 알려진 함정이 있고, 이를 명시적 프레임으로 방지했다.
- **high = MAX, low = MIN, volume·quoteVolume·tradeCount·takerBuyQuote = SUM** (전부 numeric).
- **진행 중 버킷 포함**: 가장 최신 버킷은 아직 채워지는 중일 수 있다(예: 1h 버킷에 12분치만 존재).
  실시간 차트의 자연스러운 동작이며, 확정 여부는 버킷 시각으로 판별 가능하다.

## 4. 계산 불가(N/A) 처리 정책

| 지표 | 계산 불가 조건 | SQL 처리 | overview (number 강제) | series |
|---|---|---|---|---|
| priceChangePct24h | 24h 전 봉 없음 / 기준가 ≤ 0 | `CASE` → `NULL` | 0 | — |
| vwap | Σvolume = 0 | `CASE` → `NULL` | 0 | 포인트 제외 |
| vwapDeviationPct | vwap 계산 불가 | `CASE` → `NULL` | 0 | — |
| realizedVolatility | 수익률 표본 < 2 / close ≤ 0 | 필터 + `CASE` → `NULL` | 0 | 포인트 제외 |
| takerBuyRatio | ΣquoteVolume = 0 | `CASE` → `NULL` | 0 (+0~1 클램프) | 포인트 제외 |
| volumeSurgeRatio | 직전 구간 합 = 0 | `CASE` → `NULL` | 0 | — |

원칙: **불가 판정은 SQL 에서 명시**(`CASE WHEN 분모 > 0 …`, `close > 0`, `n >= 2`)하고,
JS 경계는 치환만 한다. `NaN`/`Infinity` 는 어떤 경로로도 프론트에 도달하지 않는다.
overview 의 0 치환은 프론트 타입 계약(`number`, non-nullable)에 따른 표시 규약이며,
시계열은 해당 포인트를 제외해 그래프가 0 으로 왜곡되지 않게 했다.

## 5. 갱신 주기와 이벤트

- 스냅샷은 `METRICS_REFRESH_MS`(기본 2초) 주기로 심볼별 재계산해 메모리에 캐시하고,
  1분봉 확정 이벤트(`kline.closed`) 수신 시 즉시 앞당겨 갱신한다.
- 갱신 시마다 내부 이벤트 **`metrics.updated`** (페이로드 `{ overview: MetricsOverview }`)를
  발행하며, realtime(SSE) 모듈이 이를 구독해 SSE `metrics` 이벤트로 프론트에 전달한다.
- 조회 API 는 캐시에서 반환하므로 트래픽이 늘어도 집계 부하는 일정하다.
